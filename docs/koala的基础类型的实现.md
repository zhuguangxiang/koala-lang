### 一、先看结论

| 维度 | Koala | Go | Rust | 合理性 |
| :--- | :--- | :--- | :--- | :--- |
| **算术：小类型运算** | 提升到 64 位，结果是大类型 | 不提升，原地 wrap | 不提升，debug panic / release wrap | ✅ 方向正确，但有代价 |
| **算术：跨符号混合** | ❌ 编译错误 | ❌ 编译错误 | ✅ **允许**（隐式转无符号） | ✅✅ Koala 明显优于 Rust |
| **算术：溢出处理** | 常量期必报错；运行时 wrap / `--int-trap` panic | 永远静默 wrap | debug panic，release wrap；需手动调用 `wrapping_*` 等 | ✅ 分层最清晰 |
| **位运算：结果类型** | 提升计算后**掩码回原位宽**，保持小类型 | 保持小类型 | 保持小类型 | ✅ 符合直觉，且比 Go/Rust 更"干净" |
| **位运算：符号混合** | ❌ 编译错误 | ❌ 编译错误 | ❌ 编译错误 | ⚖️ 三家一致，合理 |

一句话：**Koala 在算术上选择了"精度优先"（像 C 的整型提升但提到 64 位），在位运算上选择了"位宽守恒"，两者组合消除了 Go/Rust 里最典型的两类数值 bug，代价是显式收窄转换变多。**

### 二、维度一：算术运算

#### 规则回顾
- `uintN op uintM → uint64`，`intN op intM → int64`，`floatN op floatM → float64`
- 跨符号族（`uintN op intM`）直接编译错误
- 字面量默认 `int64` / `float64`
- 常量表达式溢出编译期报错；变量运行期默认 wrap，`--int-trap` 下 panic

#### 与 Go 的差异

| 点 | Go | Koala | 评价 |
| :--- | :--- | :--- | :--- |
| 小类型加法 | `var a,b uint8; a+b` 结果仍是 `uint8`，**原地截断**（`200+100 = 44`） | 结果是 `uint64`，`200+100 = 300` | Koala 胜。Go 的这种行为是 checksum、图片混合、环形缓冲之外最常见的静默错误源 |
| 默认类型 | 字面量默认 `int`（平台相关，32/64 位不同） | `int64`，固定 | Koala 胜。Go 在 32 位机上 `int` 是 32 位，跨平台行为不一致 |
| 溢出检查 | **完全没有**，永远静默 wrap，标准库只有 `math/bits` 辅助 | 常量期硬错误 + `--int-trap` | Koala 胜出一个数量级 |
| 跨符号比较 | 禁止（类型必须相同） | 禁止 | 打平 |

#### 与 Rust 的差异

| 点 | Rust | Koala | 评价 |
| :--- | :--- | :--- | :--- |
| 小类型加法 | 不提升，`u8 + u8 = u8`；debug 模式 panic，release wrap | 提升为 `u64`，永不溢出（除非本身就是 64 位） | 各有取舍：Rust 保留模运算语义但需要五套 API（`wrapping_`/`saturating_`/`checked_`/`overflowing_`/`as`）；Koala 用类型提升换掉 API 复杂度 |
| **跨符号比较** | **允许**！`(-1i32) < (2u32)` 编译通过，结果为 `true`（-1 被转成 4294997295） | 编译错误 | **Koala 完胜**。这是 Rust 生态里反复出现的真实 bug 类，也是 Rust 官方承认的历史包袱 |
| 默认类型 | 字面量默认 `i32`（不是 64 位） | `int64` | Koala 更贴合现代 64 位机器和主流业务 |
| 严格模式 | 靠构建 profile（debug/release）区分，粒度粗且不可控 | `--int-trap` 编译标志，语义明确 | Koala 更可控 |

#### 合理性评估

**✅ 合理的部分**
1. **中间计算不丢精度**是几乎所有开发者的心智预期。`a + b` 不该比数学上的 `a+b` 小。
2. **跨符号族禁止**单条规则就能消灭一大类 CVE，成本为零。
3. **常量期硬错误不可关闭**——这是唯一能"零成本消除已知错误"的层次，设计正确。
4. 与 C 的整型提升（integer promotion）同源，不是凭空发明，编译器实现路径成熟。

**⚠️ 需要警惕的部分**
1. **语义断裂感**：`uint8(2) - uint8(3)` 在 Go/Rust/C 里是 `255`（模运算，符合"字节算术"直觉），在 Koala 里是 `uint64` 的 `18446744073709551615`。哈希、CRC、校验和、密码学、像素混合这类**依赖模运算**的代码会全部变味，必须每步显式收窄。这是最大的可用性代价。
2. **回写负担**：`c = uint8(a + b)` 会成为高频写法。好在编译器可以做常量传播优化（已验证 `test_int_1` 坍缩成一条立即数返回），性能无损，但源码噪音真实存在。
3. **64 位本身仍会溢出**：提升只能保护到 64 位。`uint64.max + 1` 或累加大循环计数时，`--int-trap` 才真正起作用。这一点必须在规范里写清楚，否则用户会误以为"Koala 的算术永远不会溢出"。
4. **性能**：64 位机器上 `uint8→uint64` 提升基本零成本（寄存器天然宽）；但在 32 位目标或密集小整数 SIMD 场景下会有开销，需要 benchmark。

### 三、维度二：位运算

#### 规则回顾
- 提升到 64 位计算 → **即时掩码回原始位宽** → 结果类型 = 操作数原始小类型
- 跨符号族同样禁止

#### 与 Go / Rust 的差异

| 点 | Go | Rust | Koala | 评价 |
| :--- | :--- | :--- | :--- | :--- |
| 结果类型 | 保持原位宽（无提升） | 保持原位宽（无提升） | 提升计算后掩码回原位宽 | Koala 多了一步，但**对外可观察结果完全一致**，只是中间不丢高位信息 |
| 移位 | `x << n`，n 可以是任意整型（有隐式转换坑） | `x << n`，n 可以是任意整型但负值/超位宽会 panic | 未实测，需明确 | ⚠️ 建议明确：移位计数强制 `uint` 且做范围检查 |
| 按位取反 | `^x`（前缀一元，与其他语言 `~` 不同） | `!x`（与逻辑非共用，靠类型区分） | 未实测 | ⚠️ Koala 无关键字，若用 `not`/`~` 需注意与布尔非的歧义 |
| 符号混合 | 禁止 | 禁止 | 禁止 | 三家一致 |

#### 合理性评估

**✅ 这是三个维度里设计得最漂亮的一个。**

1. **"掩码回原位宽"等于宣告：位运算是位级操作，不是数值操作。** 位运算的语义由位宽定义，不由数值大小定义。`uint8(0xFF) & uint8(0x0F)` 必须是 `uint8(0x0F)`，不能因为中间提升成 64 位就变成 `0x0F_u64` 导致后续类型链污染。Koala 的做法既享受了提升带来的中间一致性，又守住了位宽的边界。
2. **与算术形成正交分工**：算术负责"值"（允许增长，所以结果变大类型）；位运算负责"位"（位宽固定，所以结果回原位宽）。这套分工有明确的物理依据，不是拍脑袋。
3. **对比 C 的陷阱**：C 里 `uint8_t a, b; auto c = a & b;` 中 `c` 的类型是 `int`（整型提升），经常导致 `~c` 或移位时出现符号扩展 bug。Koala 直接杜绝了这一类问题。

**⚠️ 唯一的不协调**：算术和位运算在"结果类型"上行为不同，初学者可能困惑。建议在规范里用一句话钉死：

> **算术运算的结果类型由"值的范围"决定（提升到 64 位）；位运算的结果类型由"位的宽度"决定（掩码回原位宽）。**

有了这句话，两条规则就不再是例外，而是一条统一原则的两个实例。

### 四、交叉验证：一个用例看穿三家

```
let a uint8 = 200, b uint8 = 100
```

| 表达式 | Go | Rust(debug) | Koala |
| :--- | :--- | :--- | :--- |
| `a + b` | `44` (uint8，静默错) | panic | `300` (uint64) ✅ |
| `a - b` | `100` | `100` | `100` (uint64) |
| `b - a` | `56`（即 -100 mod 256） | panic | `18446744073709551516` (uint64) ⚠️ |
| `a & b` | `32` (uint8) | `32` (u8) | `32` (uint8) ✅ |
| `^a` / `~a` | `55` | `55` | 待实测 |
| `a < 250`（字面量） | ✅ | ✅ | ✅（字面量适配目标类型） |
| `a < int8(100)` | ❌ | ❌ | ❌ |

**关键观察**：Koala 在"加法"上更安全，在"减法产生负数"上更**显眼**——它不会给你 255 也不会 panic，而是给你一个巨大的 `uint64`。这属于"把错误变成另一个类型的正确值"，严格说并没有更安全，只是**更容易在后续比较/转换中被发现**（因为跨符号比较会报错，巨大的值也很容易在测试中暴露）。这一点值得在文档里诚实说明。

### 五、最终判定

| 维度 | 评分 | 理由 |
| :--- | :--- | :--- |
| **算术运算** | **8.5/10** | 提升策略 + 跨符号禁止 + 分层溢出检查，整体优于 Go/Rust；扣分项是模运算语义丢失带来的回写负担，以及 64 位边界仍需 trap 兜底 |
| **位运算** | **9.5/10** | 提升计算 + 掩码回位宽，既避免 C 的类型污染，又守住位宽边界，三家最优 |
| **两者组合的一致性** | **9/10** | 有清晰的统一原则（值 vs 位）可解释，只需在规范里明确表述 |

**三条落地建议**

1. **补一条显式模运算语法糖**（如 `a +% b` 或 `uint8.add_wrap(a, b)`），给密码学/哈希/环形缓冲让路，否则这些场景会被迫写满 `uint8(a + b)`。
2. **明确移位语义**：计数类型、超位宽行为、负值处理——这是位运算唯一还没钉死的缺口。
3. **在规范里写明"提升只保护到 64 位"**，并给出 `uint64` 溢出的示例与 `--int-trap` 的必要性，防止用户形成"Koala 算术永不出错"的错误心智模型。
