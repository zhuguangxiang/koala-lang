# PyTorch 能力在 Koala 中的支持方案：重点是算子融合和图编译

## 一、结论先行

PyTorch 要做 `torch.compile`，最难的一步是在运行时从 Python 字节码里把计算图抓出来（TorchDynamo 负责这件事）。原因是 Python 没有静态类型，只能边执行边猜。

Koala 情况相反。它本来就有带类型的 SSA IR（KLR）、一套 pass 管理器（`opt/pass.c`），以及能内联的 `opt/inline.c`。只要 Tensor 由编译器内置，dtype 又按方案 A 静态化，那么"抓图"这一步可以在编译期直接从 KLR 中提取，不需要运行时追踪。

**所以我的方案是**：

- 以**编译期静态抓图**为主，运行时追踪只作补充；
- 中间新加一层独立的 **Tensor 图 IR（TIR）**；
- 后端按"分块解释执行 → JIT 生成 SIMD 循环 → AOT 生成 C"的顺序推进。

整条路线和 PyTorch 2 的分层一一对应，但抓图这一层可以做得更简单、更可靠。

## 二、PyTorch 能力和 Koala 方案对照

| PyTorch 组件 | 职责 | Koala 方案 | 难度 |
|---|---|---|---|
| ATen / eager 内核 | 逐个算子用 C 内核执行 | M0 T0–T2 的 native 内核，加 `OP_TENSOR_*` 专用 opcode | 已规划 |
| autograd（运行时 tape） | 动态图上的反向求导 | Tensor 节点挂 `grad_fn`，运行时 tape；`with no_grad()` 复用现有 `with` 语句（`Withable`） | 中 |
| TorchDynamo | 从 Python 字节码抓图，遇到抓不了的地方切断（graph break），并生成守卫（guard） | **编译期从 KLR 提取 TIR**。graph break 由静态分析决定；守卫只检查形状，因为 dtype 已经是静态的 | 中（比 PyTorch 简单） |
| FX Graph | 图 IR | **TIR**：纯数据流 DAG，节点是 Tensor 算子，带符号化形状 | 中 |
| Functionalization | 把原地修改和 view 转成纯函数形式 | TIR 上的 functionalize pass，处理 `-=` 和 view 别名 | 中高 |
| AOTAutograd | 在图层面推导反向图，前向和反向一起优化 | 在 TIR 上为每个算子写反向规则，生成联合图，做保存还是重算的决策 | 高 |
| TorchInductor | 融合、调度、代码生成 | 融合分组、内存规划，再接 3 个后端（见第五节） | 高 |
| Triton / C++ 代码生成 | 生成内核代码 | ① 分块解释执行（NumExpr 风格）② JIT 用 `emit.c` 生成 SSE2/AVX2 循环 ③ AOT 生成 C 再编译 | 分阶段 |
| guards 和重编译缓存 | 形状变了就重新编译 | 以形状签名为键缓存；先按具体形状特化，后续再做符号形状 | 中 |
| nn / optim / DataLoader | 训练栈 | 已在原文档 §11.3 规划，用纯 Koala 加 Tensor 实现 | 中 |
| 设备后端 | CUDA 等 | TIR 作为统一入口，接 ggml/CUDA（原文档 §11.9） | 远期 |

## 三、整体架构

```
Koala 源码
  │ parser / 类型检查（Tensor 内置，dtype 静态）
  ▼
KLR（带类型的 SSA）──内联──▶ 扩大可抓图的区域
  │
  ├─[抓图 pass] 找出由 Tensor 运算组成的最大连续区域 ──▶ TIR 子图
  │     不能放进图的位置成为 graph break：非 Tensor 副作用、未内联的调用、
  │     依赖 Tensor 值的控制流（如 .item() 进了 if）
  ▼
TIR（纯数据流 DAG，带符号形状）
  │ 1. 形状推断（符号形状 n、m 以及广播约束）
  │ 2. Functionalize（原地修改 / view → 纯函数形式 + 末尾写回）
  │ 3. 规范化：常量折叠、公共子表达式消除、死代码消除、代数化简
  │ 4. [训练] AOT 反向：生成联合图，决定保存还是重算
  │ 5. 融合分组
  │ 6. 内存规划：中间缓冲复用、原地化
  ▼
已编译的图（kernel 列表 + 缓冲计划 + 守卫）
  │ 序列化进 klc，作为常量
  ▼
运行时：OP_TENSOR_GRAPH 调用
  ├─ 守卫检查（形状签名、是否连续、是否有别名）── 不通过 ──▶ 退回 eager 路径
  └─ 通过 ──▶ 后端执行：分块解释 / JIT 生成的 SIMD 内核 / AOT 生成的 C
```

**守卫不通过时一定退回 eager 路径**。这样不管编译图出什么问题，语义都和 eager 一致，相当于 PyTorch 的 fallback。

## 四、算子融合方案（重点）

### 4.1 TIR 中算子的分类

借鉴 Inductor 的做法，按"能不能融合"把算子分成几类：

| 类别 | 示例 | 融合规则 |
|---|---|---|
| Pointwise（逐元素） | `+ - * / neg exp log sqrt abs` 以及比较运算 | 可以和任意多个 pointwise 自由合并 |
| Broadcast / view | 广播、`reshape`、`.T`、切片 | 不产生计算，只改变索引表达式，直接并入下游 |
| Reduction（归约） | `sum mean max argmax` | pointwise 可以作为它的前段并入（prologue） |
| 复杂算子 | `matmul`、后续的 `conv` | 不和其他算子融合，但后面跟的 pointwise 可以并进来（epilogue，如 `relu(X@W + b)`） |
| 边界 | `.item()`、`tolist()`、打印 | 必须把结果算出来，在这里切断 |

### 4.2 融合算法（v1 保持简单，规则确定）

1. **按拓扑序贪心合并**。如果一个 pointwise 节点只有一个消费者，并且迭代空间相同（广播之后的形状一致），就把它并入消费者所在的组。
2. **有多个消费者的节点：重算还是保存**。
   - 计算代价低（例如不超过 3 个 pointwise 运算）就在每个消费者里重算一遍；
   - 否则把结果存下来，作为组的边界。
   - 以 M0 的 demo 为例，`err` 有两个消费者：`(err*x).mean()` 和 `err.mean()`。最优做法是**把两个归约放进同一个循环里同时算**（多输出归约），这样 `err` 一次都不用存下来。
3. **归约 prologue**：`(err * x).mean()` 整个成为一个"逐元素计算后归约"的内核。
4. **不融合的情况**：存在别名写入；跨 graph break；迭代空间不一致；被融合的部分含有 matmul 本体。

### 4.3 M0 demo 上的效果

```
let err = x * w + b - y          # eager：3 个内核，3 个临时数组
w -= 0.01 * (err * x).mean()     # eager：2 个内核，1 个临时数组
b -= 0.01 * err.mean()           # eager：1 个内核
```

| | 内核数 | 临时数组 | 读写内存的遍数 |
|---|---|---|---|
| eager | 6 | 4 个，每个长度为 n | 约 10 遍，每遍 n 个元素 |
| 融合后 | **1**（多输出归约：一个循环里同时求 Σerr·x 和 Σerr） | **0** | **2 遍**（读 x 和 y） |

这就是内置化以后最主要的收益：主要省在内存带宽和临时数组分配上，不是省在计算上。

### 4.4 数值正确性约定

- **pointwise 融合必须和 eager 的结果逐位一致**：保持相同的运算顺序，不做 FMA 合并（或者明确提供开关）。
- **归约**：分块、SIMD 归约会改变浮点加法的结合顺序，结果和 eager 只能做到误差容限内一致。提供 `KOALA_TENSOR_DETERMINISTIC=1`，强制按 eager 的顺序做归约。
- **差分测试框架**：每个测试用例都跑 eager 和 compiled 两条路径并对比结果，加入 `./test-debug.sh`。同时提供 `KOALA_TENSOR_FUSE=0` 全局关闭融合，用于二分定位问题。

## 五、后端：三档，按顺序推进

| 档位 | 原理 | 优点 | 代价 |
|---|---|---|---|
| **B1 分块解释执行（先做）** | 融合后的内核描述成一段很短的"微操作序列"，C 运行时以 256 到 1024 个元素为一块逐块执行，块内是紧凑的 C 循环（NumExpr 的做法） | 不需要生成代码，可移植；已经能拿到大部分内存带宽收益（临时数据留在 L1 cache）；可以序列化进 klc；不违反 JIT 的 GC 不变量 | 每块有一次微操作分发的开销，比真正生成的代码慢 1.5 到 3 倍 |
| **B2 JIT 生成 SIMD 循环** | 复用 `src/jit/emit.c`，为融合内核生成 SSE2/AVX2 循环 | 最快；内核是叶子函数，循环内不分配内存、不调用 helper，**天然满足 JIT DESIGN.md §1 的不变量 1、2**（没有 GC 点） | 要扩展 `emit.c` 的向量指令编码；只支持 x86-64 |
| **B3 AOT 生成 C** | 编译器（koalac）为每个融合内核生成 C 代码，调用系统 cc 编译成 .so 并缓存 | 能利用 cc 的自动向量化，跨平台 | 运行环境要有 C 编译器；需要缓存和失效管理 |

建议 B1 先上线，作为正确性基线和兜底；B2 只在 bench 证明值得时再做；B3 作为发布和跨平台的选项。三档共用同一份 TIR 和融合结果，只有代码生成这一步不同。后续 GPU 后端（ggml/CUDA）也接在这一层。

## 六、抓图：静态提取为主，运行时追踪为辅

| 方式 | 机制 | 结论 |
|---|---|---|
| **静态提取（主）** | 在 KLR 上，按 `type_is_tensor` 圈出由 Tensor 值组成的最大区域，先内联扩大区域，再降成 TIR | 零运行时开销，graph break 在编译期就能确定并打印出来（类似 `torch._dynamo.explain`）。函数默认开启，用 `@eager` 注解关闭 |
| `@compile` 注解 | 对整个函数（包括循环）做更激进的抓图：展开固定次数的循环，跨基本块 | 第二阶段再做 |
| 运行时追踪 / Lazy Tensor（辅） | 记录算子，遇到需要取值时才执行（类似 PyTorch/XLA 的 LazyTensor） | 只在静态提取覆盖不了的动态代码（如高阶函数、闭包）里用；有每轮重新哈希图的开销，**v1 不做** |

**graph break 的明确规则**：

- 调用了未内联的非 Tensor 函数；
- 有副作用，比如 IO、写全局变量、写对象字段；
- `.item()` 或 `tolist()` 的结果流进控制流；
- 异常边界；
- 跨 `yield` 或协程挂起点（和并发计划交互）。

**守卫**：

- dtype 是静态的，不用检查；
- 需要检查的是形状签名（秩和各维大小）、是否连续、输入之间有没有别名；
- v1 按具体形状特化，每个图缓存 8 个形状变体，超出后退回 eager；
- v2 引入符号形状，例如训练时最后一个 batch 变小，不需要重新编译。

## 七、autograd 和图编译的结合

1. **先做 eager autograd**（对应原文档 §11.2）：运行时 tape，`backward()` 在 tape 上执行。这是正确性基线，也是不能抓图的代码的兜底。
2. **AOT 反向**：在 TIR 上为每个算子登记反向规则，生成"前向 + 反向"联合图，然后整体做融合和内存规划。
   - 广播的反向是"按轴求和"，pointwise 的反向仍然是 pointwise，所以前向和反向可以一起融合。
   - 保存还是重算：v1 的规则是"pointwise 结果在反向里重算，归约和 matmul 的结果保存"；v2 再做 min-cut 求最优。
3. **课程作业作为天然的测试集**：对比手写梯度、eager autograd、编译后的 autograd，三者结果要互相吻合。

## 八、分阶段路线（接在现有 M0 后面）

| 阶段 | 内容 | 前置 | 验收 |
|---|---|---|---|
| F0 | eager 内核和专用 opcode，即 M0 的 T0–T2 | — | M0 demo；bench 基线 |
| **F1** | TIR 定义；静态提取（只在基本块内、只抓 pointwise 和归约）；融合分组；**B1 分块解释后端**；差分测试框架 | F0、M0.5（广播） | M0 demo 合成 1 个内核；和 eager 逐位一致（归约在容限内）；bench 显示临时数组分配降到 0 |
| F2 | functionalize（原地修改和 view）；内存规划；graph break 报告工具 | F1、view 语义 | `theta -= ...` 和切片 view 场景，eager 与 compiled 结果一致 |
| F3 | eager autograd 和 nn/optim | M1 | 课程 lab 的手写梯度和 autograd 结果吻合 |
| F4 | AOT 反向、联合图融合、保存还是重算 | F2、F3 | MLP 训练中 compiled 与 eager 的损失曲线在容限内一致，速度提升 |
| F5 | B2 JIT SIMD 后端，matmul epilogue 融合 | F1 bench 数据 | 相对 B1 的加速比 |
| F6 | `@compile` 跨基本块抓图，符号形状 | F4 | 最后一个 batch 变小时不重新编译 |
| F7 | B3 AOT 生成 C、设备后端（ggml/CUDA） | F5 | 见原文档 §11.9 |

**和现有文档的关系**：原文档 §13 中的 T3（在 KLR 上做融合 pass）**改为 F1**。融合不再直接在 KLR 上改写，而是"从 KLR 提取 TIR，在 TIR 上融合，生成 `OP_TENSOR_GRAPH`"。这样 KLR 的优化 pass 不受影响，融合逻辑集中在 TIR 一层。

## 九、风险

| 风险 | 缓解 |
|---|---|
| 别名和 view 让融合出错，这是最常见的 bug 来源 | F1 只融合没有 view、没有原地修改的区域；F2 先做 functionalize 再放开限制；用差分测试兜底 |
| 浮点归约顺序变化导致回归测试结果不稳定 | 归约测试按误差容限断言；提供确定性开关 |
| klc 格式里要嵌入编译好的图，带来版本兼容问题 | 编译图的序列化单独带版本号，版本不匹配时退回 eager |
| 守卫、缓存导致的重编译风暴 | 每个图限制变体数，超出就固定走 eager，并打印诊断信息 |
| B2 扩展 `emit.c` 的向量指令编码，工作量和出错面都大 | 先拿 B1 的 bench 数据证明有必要；内核是叶子函数，不碰 JIT 不变量 |
| 和你正在做的 switch WIP 冲突（`irgen.c`、`parser_expr.c`） | 抓图 pass 是新文件（如 `opt/tensor_capture.c`、`tir/*.c`），不改既有 pass |
| 并发：GC 是单线程的（`gc.c:16`），融合内核以后做多线程 | 内核内部不分配对象、不进入 GC 点，可以安全并行；线程模型按并发计划另行立项 |
