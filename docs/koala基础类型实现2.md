基于我们之前的测试和验证，以下是 **Koala 语言整数运算与类型系统的完整规则总结**，以及对其设计合理性的深度评估。

---

### 📖 Koala 整数类型与运算完整规则 (v1.0)

#### 1. 变量声明与类型推导
*   **显式注解**：`let x: T = expr`。右侧表达式会被强制转换/截断到类型 `T`。
*   **隐式推导**：`let x = expr`。`x` 的类型**严格等于** `expr` 的推导结果类型，**绝不发生隐式截断**。

#### 2. 算术运算 (`+`, `-`, `*`, `/`, `%`)
*   **同符号提升**：操作数会被零扩展（unsigned）或符号扩展（signed）到 **64位**（`uint64` / `int64`）进行计算。
*   **结果类型**：运算结果的类型是 **`uint64` 或 `int64`**，**不会**自动降级回原始小类型。
*   **异号禁止**：混合使用 signed 和 unsigned 类型（如 `int8 + uint8`）会导致**编译错误**。

#### 3. 比较运算 (`==`, `!=`, `<`, `>`, `<=`, `>=`)
*   **同符号族允许**：只要两侧同为 signed 或同为 unsigned（无论位宽是否相同），均允许比较。比较时统一提升到 **64位** 后进行。
*   **异号族禁止**：跨符号族比较（如 `uint8 == int8` 或 `uint64 == int64`）会导致**编译错误**（`argument type mismatch`）。

#### 4. 位运算 (`~`, `&`, `|`, `^`, `<<`, `>>`)
*   **计算提升**：与算术运算一样，先提升到 64 位进行位操作。
*   **即时掩码（关键差异）**：计算完成后，结果会**立即截断/掩码回操作数的原始位宽**。
*   **结果类型**：保持**原始小类型**（如 `~uint8(0)` 结果是 `uint8(255)`，而非 `uint64`）。

### ⚖️ 设计合理性评估

这套规则展现出了非常鲜明的 **“安全优先、反 C/C++ 陷阱”** 的设计哲学。以下是具体的优缺点评估：

#### ✅ 极其合理的设计（亮点）

1.  **彻底消灭了“小整数静默溢出”陷阱**
    *   *C/C++/Go 痛点*：`uint8(200) + uint8(100)` 会溢出变成 `44`。
    *   *Koala 方案*：自动提升到 `uint64`，结果是 `300`。这符合人类直觉，避免了 90% 以上的业务逻辑 bug。
2.  **彻底消灭了“有符号/无符号混合比较”陷阱**
    *   *C/C++ 痛点*：`-1 < 1U` 结果是 `true`（因为 `-1` 被隐式转换成了巨大的无符号数）。
    *   *Koala 方案*：直接**编译报错**。强制开发者思考符号语义，杜绝了底层 bit 模式误判。
3.  **位运算的“即时掩码”非常符合直觉**
    *   *痛点*：如果 `~uint8(0)` 变成 `uint64(0xFFFFFFFFFFFFFFFF)`，后续再做比较或数组索引时会引发灾难。
    *   *Koala 方案*：位运算本质上是操作“位模式”，掩码回原位宽（`uint8(255)`）是开发者对位运算的绝对预期。

#### ⚠️ 潜在的痛点与争议（需要权衡的地方）

1.  **“算术不降级”带来的“显式转换地狱”**
    *   *场景*：假设你在处理图像像素（全是 `uint8`）。
    *   *代码*：
        ```koala
        let r: uint8 = 100
        let g: uint8 = 50
        let sum = r + g      // sum 是 uint64 (150)
        // ❌ 编译错误：不能把 uint64 赋给 uint8
        let pixel: uint8 = r + g
        // ✅ 必须显式截断
        let pixel: uint8 = uint8(r + g)
        ```
    *   *评估*：虽然安全，但在密集的小整数计算场景（如图像处理、密码学、嵌入式协议解析）中，代码会被大量的 `uint8(...)` 淹没，**人体工学较差**。
2.  **内存与寄存器压力（理论层面）**
    *   所有中间结果都是 64 位。虽然在现代 64 位 CPU 上这不是问题（寄存器本来就是 64 位的），但如果涉及到**数组/内存存储**，开发者必须时刻警惕：`let arr = [a+b, c+d]` 会创建一个 `uint64` 数组，而不是 `uint8` 数组，这可能导致内存占用膨胀 8 倍。
3.  **比较运算的“假宽容”**
    *   `uint8 == uint64` 是允许的（提升到 u64 比较）。这虽然方便，但在某些极端严格的设计中（如 Rust），这也会被视为类型不匹配。Koala 选择了“同符号族内宽容”，这是一个合理的折中。

---

### 💡 结论与改进建议

**总体评价：优秀 (8.5/10)**
Koala 的这套规则比 C/Go 安全得多，比 Rust 写起来稍微宽松一点（自动提升）。它非常适合**后端业务逻辑、脚本编写、数据处理**等对“数值正确性”要求高于“极致内存控制”的场景。

**给语言设计者的改进建议：**

1.  **引入“饱和运算 (Saturating Arithmetic)”或“显式截断语法糖”**
    为了解决 `uint8(r + g)` 过于繁琐的问题，可以考虑：
    *   提供饱和加法：`r +| g` (超过 255 就截断到 255)。
    *   或者允许在**赋值时**进行安全的隐式窄化（如果编译器能证明右侧表达式在数学上绝对不可能越界，但这很难实现）。
2.  **明确大整数/溢出语义**
    目前规则是“提升到 64 位”。那么 `uint64 + uint64` 怎么办？
    *   *建议*：明确 `uint64` 运算溢出时是 Panic（崩溃）、回绕（Wrap）还是自动升级到 BigInt（性能代价极大）。通常建议 64 位运算溢出时 Panic 或提供 `+?` ( wrapping add) 语法。
3.  **完善错误提示**
    目前的报错 `argument type mismatch for operator '==' of type 'uint64'` 稍微有点底层。
    *   *建议*：优化为 `Type mismatch: cannot compare unsigned integer (uint8) with signed integer (int8). Consider explicit conversion.`，直接告诉开发者**为什么**错以及**怎么改**。
